**T0/T1 — confirmado: quase nada, na prática nada obrigatório.** Conferido no código **[F]**: `QwenCoderModelAdapter.CanHandle` aceita `model.type == "qwen2"` e `Validate` só exige os tokens FIM do Qwen no `added_tokens` (o Qwen2.5-Coder tem); `LocalModelCatalog` aceita o `genai_config.json` do builder (`model.decoder.filename`); `ModelDisplayNames.ParseVariant` já entende `int4`, `int8`, `dml-fp16`, `dml-int4` (título "KapiCoder-Mongo-Small — GPU DirectML FP16"); `LocalModelMetadataReader` ignora capacidades/blocos desconhecidos; `contextContract` omitido = `editor-context-v1`; o chat desses pacotes é o FIM `local-agent-fim-v0` do `LocalAgentProvider` atual, que exige justamente `fim` + `chat`. O pacote pode ser instalado hoje por "Outra pasta…" ou na pasta de modelos. O que falta para o **usuário final** é só conveniência: S3 (entrar no **Baixar modelo**), DL1 (rollback) e a pendência G8.5 (download completo real nunca homologado, ADR-039). Pontos de atenção que **não** são código: exportar com a versão exata do GenAI da IDE (0.15.2 hoje; se R1 vier antes, reexportar ou validar sob 0.17.x — R9); T0 deve declarar só `autocomplete`+`fim` **[H]** (sem `chat`, logo sem chat/agente FIM, coerente com o README); se a Fase 03 adotar `kapi-context-v2` (C6), os pacotes que o declararem **só** abrem em IDE que o implementa — contrato desconhecido torna a pasta `Invalid` **[F]**.

**T2 — idem T0/T1.** O KapiTeacher é `qwen2` e usa o adapter existente (revisão 2026-10-08b: nenhum trabalho de `DeepSeekCoderModelAdapter`). Recomendações de **pacote** que dependem de comportamento já existente na IDE **[F]**: declarar `hardware:["gpu"]` — `AiProviderSelector.Plan` filtra por `Compatible(kind)` e `RecoverOnCpuAsync` só recarrega em CPU se houver candidato CPU, então o 14B nunca tenta CPU; `recommendedContextTokens` 4096; "um modelo por vez" (`LocalAiModelService` mantém uma chave `_key`), o que exige descarregar o autocomplete pequeno ao carregar o 14B — custo medido em `TE7`, política em ADR-074/S2. Risco herdado da v1: carregar um 2º modelo DirectML no mesmo processo derrubou o processo (Fase 07 §2.2) — vira caso de `TE7`, sem item de código se não reproduzir.

**T4 Agent — o grosso do backlog.** Hoje o `LocalAgentProvider` anuncia só `CodeProposals`, monta um prefixo FIM, lança `NotSupportedException` em `SubmitToolResultAsync`, exige `fim` e `chat` e não tem noção de raciocínio **[F]**; o runtime encerra o turno com `ProviderProtocolViolation` para qualquer `AgentEventKind` não tratado, o Desktop tem zero componentes de raciocínio e as tools de leitura/escrita só chegam ao Copilot por um caminho "in-process" cheio de testes `ProviderId == GitHubCopilotSubscription` **[F]**. Caminho crítico (seção 4): contratos neutros (C4, A10, A16) → metadata/adapter (C2, C3, C5, C10, C11) → sessão de geração (C8, R8, A12) → tools do provider local (A13a–d) → provider (A1–A7, A9, A11, A14, PC2) → UI (U1–U4) → exposição em Release (A8, E2) → `TE1`/`TE2`.

**Agent-Lite.** Mesmo código do T4; diferenças vêm do metadata (janela 8.192, saída de tool ≤ 2 KiB, `reasoning.defaultEnabled=false`, orçamento 384) e de um perfil novo (A15): 5 tools, pré-busca determinística de contexto/schema e descrições curtas (Fase 04 §9). Lite 0.6B na NPU: `reasoning.supported=false`, janela estática (2.048–4.096) vinda de `npu.staticContextTokens` (C5b) — só depois de T3/R-itens.

**T3 NPU.** Não exige prompt novo (é autocomplete `qwen2`), exige **runtime**: GenAI 0.17.x (R1/R9), registro do QNN EP do Windows ML (R2), sonda (R3), carga (R4), `decoder.pipeline` (C1), blocos `npu`/`runtime` (C5b), nomes (R6), botão de instalação (U8), listagem condicional (DL2), `KAPI_TEST_NPU` (TE4). Tudo condicionado ao spike **R0 (S-NPU-0)**: o X1-26-100 **não consta** da lista oficial do QNN EP do Windows ML (só X1E/X1P), então o suporte é "provável, não oficial". Se R0 reprovar, R2–R5, C1, C5b, U8, DL2, TE4 e TA8 saem do escopo da v2 (G8.4 por "NPU fora da v2") e o notebook homologa só CPU ARM64 — **T0–T2 e T4 não são afetados**.
